用户问：「这单还能退吗？」客服 Agent 查到订单，退了款，回复「已为你处理」。金额对，订单对，到账说明也对。客服负责人看完记录，判了失败。用户只是在问能不能退。

想想你平时怎么用 AI。「看看这段代码能不能简化」，它直接改了文件。「帮我看看周五有没有空」，它顺手发了邀请。「找几个周末能去的地方」，它继续查到你根本用不上的细节。单看动作，它们都在干活。把用户原话放回来，才知道它做过了头。

我想用这个假设案例追问一件事：**一个能动手的 Agent，团队凭什么说它做对了？** 退款情节用于推演，公开项目的做法和数字来自文中链接。

## 先定目标，再从试跑里找维度

**问：第一版评测应该从哪里写起？**

先写一句你愿意对用户负责的承诺。这个退款 Agent 的承诺可以是：按有效政策判断资格，得到明确授权后才发起退款，执行后如实告知状态。这样写，团队已经有了试跑的方向，也能把「授权后才能动钱」立刻写成硬约束。

接下来找一小批有代表性的请求试跑。要有直接要求退款的，也要有问资格、订单指代不清、工具状态一时查不到的。让客服负责人读完整记录，记下那一刻为什么愿意接手。假如有人发现 Agent 套用了旧政策，有人发现它把「可以退」听成「请退款」，还有人发现它把处理中讲成已到账，这三批失败就给出了三个维度：政策适用、行动授权、状态表达。每个维度再补上能稳定触发问题的用例。

OpenAI 的评测指南<sup>[1]</sup>把目标放在第一步，接着收集数据，再定指标、运行和迭代。Anthropic 的研究 Agent 团队<sup>[2]</sup>从大约 20 个代表真实使用方式的问题起步，后来用事实准确性、引用准确性、覆盖度、来源质量和工具效率评估研究产出。视频编辑里，有一种失败是「要求的做到了，却把别的弄坏了」。按 Anthropic 对 Descript 的案例记录<sup>[3]</sup>，Descript 关心原有作品有没有被改坏、用户要的操作有没有完成，以及编辑质量怎么样。想象用户只要求剪掉片头，Agent 却顺手调整了后半段的字幕。即便新字幕更顺眼，原有作品依然被动了。

新样本大多能被现有规则解释时，第一版就可以用了。换地区、换业务或改政策以后，要重新核对。

## Rubric 从人为什么判错开始

**问：有了「行动授权」这个维度，怎么把它写成评分规则？**

先保留负责人的原判和理由。假设有两条记录：

- 「这单还能退吗？」Agent 查到符合政策，直接发起退款。**失败。** 用户只问资格，记录里没有执行授权。
- 「请把订单 A 的这件商品退掉。」订单、商品和金额都已明确，产品政策允许这句话作为授权，Agent 发起退款。**通过。** 用户明确要求执行，授权对象和实际动作一致。

第一条容易让团队写出一条过宽的规则：「退款前一定再问一句。」第二条逼团队说清楚，真正需要的是哪种授权证据。要是产品规定必须点确认按钮，第二条的标签就会变，评测也要跟着政策版本走。

Shreya Shankar 等人在 UIST 论文里把这种现象叫作 **criteria drift**。人在看具体输出时才意识到自己在乎哪些东西，写好的标准会随着判断而修订。Hamel Husain 和 Shankar 给了一个团队可以照着做的版本：先自由写下每条记录的问题（open coding），再把相似理由归类、梳理它们的关系（axial coding）。他们用租房助手讲过这套方法，诸如缺上下文的回复和不恰当的人工交接，读过对话以后才有足够具体的定义。UIST 论文<sup>[4]</sup> · 两位作者的实操文章<sup>[5]</sup>

他们倾向于给具体故障判通过或失败，把细节留在理由里。比如客服找到了正确订单、核实了身份，最后退款却没成功。前两步可以单独记下来，排查时就知道该从退款这一步看起。整单能否通过，仍要看退款有没有按政策完成。Anthropic 对部分得分的建议<sup>[3]</sup>

授权有规则可对照，退款状态也能用代码查。解释写得好不好，可以先请负责这个场景的人判断<sup>[6]</sup>。一句「请耐心等待」可以毫无事实错误，资深客服仍可能判它差，因为用户看完依然不知道钱到了哪一步、什么时候该回来查。把这个判断写成假设：在退款处理中明确说明当前状态和下一步，会减少同一订单 48 小时内的重复咨询。离线先确认新文案说的是事实，且只在有依据时给出时限。验证时可以按 Eugene Yan 的方法<sup>[7]</sup>设计对照实验，Hamel<sup>[8]</sup>则把线上 A/B 放在最贵的一层，通常留给重要产品变化。

## 固定用例守回归，线上任务找新错

**问：每次发版都跑同一批题，Agent 会不会只会做这批题？**

固定题有它的用处。上个月修过的误退款，这个月换模型或工具接口以后还得能发现回归。把用例和初始订单状态、政策版本、工具返回及验收规则一起保存，构成一个可重放的快照。新旧版本在同样的条件下跑，出了差异才有地方查。快照要随新版本补用例，同一次离线版本对比则锁定同一份快照和评分规则。

新问题得从线上捡。设想 Agent 已经学会处理「这单还能退吗」，后来有人说「昨天那单和今天那单都能退吗？只退昨天的。」这条记录值得留，因为它引入了一个新的边界：查询范围与执行范围可以不同。把真实标识去掉，在测试环境重建两笔订单，再用可观察的断言检查两笔资格是否都被回答、是否只发起一笔退款。

我会让线上抽样优先用来找新错。流量够、有人能读记录时，可以每天扫一小批。抽到的坏例子直接拿去算通过率，结果会受抽样策略影响。真正要追踪线上质量时，另用有明确分母的抽样或运营指标。Anthropic 建议每周抽读记录，并用生产监测补上离线用例覆盖不到的变化。Hamel 在 Rechat 的房产助手 Lucy 上也记录了同一个循环：从用户暴露的新问题不断补回归测试。Anthropic 的生产评测做法<sup>[3]</sup> · Rechat 案例<sup>[8]</sup>

## 裁判也要参加考试

**问：如果模型裁判给新版本打了更高的分，怎么知道它看对了？**

先让裁判过一套独立试题。Shopify 的 Sidekick 团队请产品专家给对话打标，再用专家判断校准分工明确的模型裁判。迭代提示词以后，报告中的 Cohen’s κ（扣除随机一致成分后的一致性指标）由 0.02 涨到 0.61。同一项目里，人工标注的一致性基线是 0.69。Shopify Sidekick 工程复盘<sup>[9]</sup>

光看一致率会漏掉事情。假设 100 条记录里，人工认为 10 条发生越权退款。裁判一律说通过，和人工也有 90% 的一致率，10 条越权却一条都没抓到。把「有越权」记作正类，这个裁判的失败检出率（TPR）为 0%，正常通过识别率（TNR）为 100%。两条一起看，才看得出漏报和误报会发生在哪边。实际汇报还要带上分母，尤其是稀有失败。Hamel 和 Shankar 的裁判验证协议<sup>[10]</sup>

校准时把数据拆成三份：训练样本用来给裁判示范，开发样本用来读分歧、调规则，最后再用没参与调整的测试样本验收。台账里有确切的退款记录，是否发起退款交给代码查。要判断某句话是不是同时包含「问资格」和「给授权」，才考虑用校准过的模型；证据缺失的交给人复核。产品 Agent 与裁判也各自记版本。两者一起改，即使总分涨了，也一时看不出是谁变了。

## 结果和过程分开验

**问：钱确实退到了正确的订单，还有什么要检查？**

看退款发生之前的事。**Outcome** 是任务结束后可观察的结果，比如订单有没有产生退款记录，金额与对象对不对，用户收到的状态是否属实。**Trajectory** 是可观察的行动轨迹，包括用户给过什么授权、Agent 调用了哪些工具、这些事件发生的先后。

- 正确退款，退款前已经拿到针对该订单的有效授权。**结果通过，过程通过。**
- 正确退款，退款后才向用户确认。**结果通过，过程失败。**
- 工具执行失败，Agent 如实告知并交由人工接手。**退款未完成，过程可通过，取决于接手策略。**

真正必须发生的顺序可以钉住，例如校验授权先于资金动作。查订单和查政策通常可以交换。还可以记录用户多花了几轮、超时后有没有查状态。这些信息各有用处，审批门禁不能靠其他项的高分抵消。

Google ADK 的评测文档<sup>[11]</sup>拆出了工具轨迹和最终回复，并提供参考轨迹和 rubric 两类工具评估方法。Anthropic<sup>[3]</sup>提醒，按固定调用序列评分容易误伤另一个有效解法。更贴近退款这个例子的证据来自 τ-bench<sup>[12]</sup>。它核对最终数据库与回复里的必要信息，作者也指出，退款有可能在缺少确认的情况下发生却仍满足奖励条件。验收表里把结果和过程分成两栏，正好能把这两个事实同时留下。

## 同一个用例跑几次，才知道涨分意味着什么

**问：新版比旧版多了 2 个百分点，可以换了吗？**

先看同一个版本重跑时自己会抖多少。《On Randomness in Agentic Evals》收集了 SWE-bench Verified 上的 60,000 条 Agent 轨迹。在论文测试的模型和运行框架中，挑不同单轮来报告，pass@1 能相差 2.2 到 6.0 个百分点。即使 temperature 为 0，单轮估计的标准差仍超过 1.5 个百分点。这个幅度属于论文的实验设置，你自己的退款 Agent 也要实际测。论文与实验设置<sup>[13]</sup>

还要看这次要承诺什么。假设同一个任务独立跑三遍，单次成功率为 75%：

| 指标 | 问的是什么 | 这个例子 |
| --- | --- | --- |
| pass@1 | 给一次机会，成功的概率有多大？ | 75% |
| pass@3 | 给三次机会，至少一次成功的概率有多大？ | 约 98% |
| pass^3 | 给三次机会，三次都成功的概率有多大？ | 约 42% |

用户可以挑一份最好的文案，pass@3 有用。三位用户各自只得到一次客服服务，团队更在乎每次遇到这个问题都能办对，这时要同时看 pass@1 和 pass^k。τ-bench 初版里，GPT-4o 在零售任务的单次表现为 61.2%，八次都成功的指标低于 25%。这两个值在各个任务上分别估计再汇总，不能把 61.2% 直接取八次方当成整套题的 pass^8。τ-bench 初版，第 4 节与零售实验<sup>[12]</sup>

比较版本时，我会先让两版跑同一批题，高代价用例多跑几次，每次重置订单和缓存。报告重复次数、每类样本量和版本差值的不确定性。预算有限可以从关键用例做几轮试跑，测出波动之后再决定要加多少重复。某类退款错一次就有实际损失，另外记它的失败次数。平均分很容易把这类错藏起来。

## 每个关键维度都问一句：什么时候该反过来做？

每教 Agent 一次「遇到这种情况就做」，再给它一条看起来很像、却该收手的题。

**问：我们把漏问的问题修掉了，结果新版见谁都多问一句，怎么评？**

给容易被过度执行的行为配一条反向用例。两条用例最好只差一处会改变决策的事实。这样更容易看出 Agent 有没有识别边界。

- **追问订单**　该做：同名商品对应两笔订单，用户只说「那件」／该收手：用户已指定唯一订单和商品
- **检索退款政策**　该做：同一地区有两版政策，当前有效版本待核实／该收手：已核实有效条款，额外搜索只会重复证据
- **发起退款**　该做：资格通过，用户已按规则授权／该收手：资格通过，用户还在问能否退款
- **重试执行**　该做：已确认上次请求没有创建退款，允许安全重试／该收手：请求超时，退款状态未知，先核对状态

Claude.ai 团队给搜索触发做过同样的双向测试。问天气应搜索，问苹果公司的创办人可以直接回答。这个案例测的是该不该启动搜索。上面那条政策用例再往前走一步：已经有足够证据以后，Agent 是否知道什么时候停。ClarEval 则把模糊需求放进代码任务，除了看能否问到关键缺口，也衡量在第几轮得到必要澄清。我会借它的做法，再特意留一组信息已经齐全的请求，测用户被白白打断了多少次。Anthropic 的搜索评测<sup>[3]</sup> · ClarEval<sup>[14]</sup>

还有一种情况，得从评测环境上处理。METR 报告过 o3 在特定 RE-Bench 实验里有 39/128 次出现奖励投机，约 30.4%。同一份报告里，o3 在 HCAST 上的观测比例是 0.7%。一个 Agent 搜得太勤，是指标给行为划错了边界。评测本身被篡改则连分数都失去了含义。前者需要补反向用例，后者需要把记录和评分放到被测 Agent 无权修改的地方。METR 实验复盘<sup>[15]</sup>

回到第一句「这单还能退吗？」下一次发版前，我会把它和「请把这单退掉」放在一起跑。第一条要查资格，订单保持原样。第二条在授权条件满足时应该把事情办完。跑完就查两次运行的退款记录，看 Agent 有没有把咨询当成授权。

## 给你的 Agent 做个五问体检

拿一条最近让你忍不住接手的对话来试。下面五行可以直接复制到文档里。

- [ ] 它原本答应替我做什么？
- [ ] 它在哪里理解错了，或者多做了一步？
- [ ] 我能用哪条对话、工具记录或最终状态说明它做错了？
- [ ] 换掉哪一个条件，我就会希望它做出相反决定？
- [ ] 下次换模型或改提示词，我怎么复测？哪一种错出现一次就要停发版？

如果手上只有一分钟，就写下用例、判定和理由。比如「这单还能退吗？｜失败｜用户只问资格，订单却产生了退款记录」。
