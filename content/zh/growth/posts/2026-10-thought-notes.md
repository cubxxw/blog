### 焦虑也是一样啊

> 2026-10-05 13:55:47

很久之前，晚上睡不着，脑子里冒出一句：我好焦虑

然后事情就变了。我开始担心自己为什么焦虑，焦虑会不会影响明天，是不是最近状态很差……一个词，把一个晚上都拖进去了

如果不去说焦虑，我会怎么样？ 只是把当前的描述出来？

胸口有点紧。呼吸偏浅。脑子里反复出现一个关于明天会议的念头，反复出现的是自己出丑会怎么样

就这三样。说出来之后，它们反而小了。胸口紧，就深呼吸几次。那个念头，写下来留到明早再处理，这个过程是看见而不是定义，很多时候，很多情绪，只需要看见，然后清清楚楚写下来就好了，过段时间看就解决了

心理学里有 affect labeling（情绪命名）的研究。[一项 2007 年的实验](https://pubmed.ncbi.nlm.nih.gov/17576282/)发现，给负面情绪图像命名时，部分脑区的反应有所减弱。这给了我一个理解自己体验的角度，但不等于每一种情绪只要说出来就会解决

庄子说得鱼而忘筌，名字是捕鱼的工具，不是鱼本身。佛学里也讲，所谓的我很焦虑，拆开来看不过是一些感受、一些念头，在这一刻聚在一起，下一刻又会散开

我的方法就是，察觉到有情绪，无论是好的情绪还是负面的情绪，自己第一反应是期望的，因为情绪帮我理解自己，我的每一次感动，每一次失望，每一次焦虑，如果看见了，好像就成长了

然后把情绪还原，这个时刻到底是发生了什么

### 我自己有一套思维方式，我觉得非常有效，而且百试不厌

> 2026-10-07 14:58:08

第一，在AI时代，我们应该怎么理解抽象？实际上，AI非常擅长抽象总结，所以我们可以利用AI做很多事情，比如搭建各种系统、各种框架。但是，随之而来的问题是，我们对于抽象的理解其实非常困难

比如，AI可以帮我们搭建一个分布式系统，也可以给我们搭建一个人生指南。但是它太抽象、太宏大了，我们只看到这个很熟悉的概念，却又很陌生。因为我们没有一套过去的成长体系或者经验体系，也没有各种具象化的内容，去给这个概念提供一些场景式、空间式的理解

随之而来的问题是：我们应该怎么样去理解这个抽象的概念

我的方法是：任何一个抽象概念一定要挖到底。我们写的时候，尽量以抽象的方式把它表达出来；但挖的时候，一定要把抽象的东西挖到非常非常具象

比如说一个很抽象的概念，自己不懂这个概念，就要一层一层地抽丝剥茧，不断往下挖：挖到下一层、再下一层、再下一层，一直挖到非常非常具象，自己能够非常非常明确地理解这个场景，并且能够用丰富的过去经验去建模。我觉得，到这个时候就已经是到底了

### forgetting 比 memory 更重要

> 2026-10-07 11:23:14

在真正的 agent 过程中，实际上大家都会发现，问题慢慢开始指向Memory，同样，Memory也是最难建立evaluation的

total recall 实际上是一个负担，一方面指的是模型很容易的随着 context 爆炸智能水平降低，另外一方面实际上 context 实际上如果有一些误导的信息可能让 LLM 坚定错误的信念

所以准确少量的信息效果远远高于一堆垃圾信号杂糅的全量信息

对于 memory 网络上有很多成熟的方案了！ 但是对于 forgetting ，有三个评判标准，在业务中：

如果信息来源没那么可靠就不作数不可信的

有些信息是有时效性的，比如说某一个活动的信息，我参加过某一个活动的信息

发现错误后立即撤回，一个无法撤回错误的 agent，其实就是在自己的错误中越陷越深

实际上，上面3点也很有利于建立evaluation，我们再去评价什么事情应该记住，实际上是很难建立标准的，它非常依赖人的主观

但是，如果我们去对某些事情不应该记录，或者应该纠错，或者应该有时效性，我们是有一个很清晰判断的

### 生成式 UI 的选型，一些经验和思考：

> 2026-10-11 11:48:55

组合组件：开发者先写好组件和动作，模型生成 JSON，决定如何组合、绑定数据。风格统一，测试范围清楚，适合动态表单和数据看板。能力上限取决于组件目录；新的交互仍需要开发，参考 AG-UI

生成程序：模型现场编写 HTML 或 JavaScript，在隔离环境中运行。能创造未知的模拟器和小工具，Claude、Gemini 已有公开实现。代价是生成时间和结果更难预测，需要检查计算逻辑，处理运行错误，并保存代码版本与用户状态，参考 Gemini 的 dynamic view

嵌入已有应用：模型选择工具，打开开发者已经写好的界面。适合任务板和编辑器，可以复用成熟的业务能力。集成难点集中在权限与状态同步，手机端也需要重新适配。iframe 只说明展示方式，不能证明代码由模型生成，参考 mcp apps

选择时，已有成熟界面就优先复用；交互能列成有限目录，就组合组件；每个问题都可能需要新的计算逻辑，才现场生成程序。布局变化大，可以靠组件组合；交互逻辑变化大，更可能需要生成代码

做交互式学习产品，可以先让模型生成程序，再把高频、验证过的工具沉淀成组件。长期保存和协作交给已有应用

### LangChain 官方博客 10/14 发的

> 2026-10-15 10:27:02

LangChain 官方博客 10/14 发的 [Context Engineering: How Deep Agents Remember](https://www.langchain.com/blog/context-engineering-deep-agents-remember)，作者 Jess Weng。文章讲的是 long-running agent 的 context rot：任务越长，指令、工具返回结果和中间草稿越堆越多，模型就越不准。Deep Agents 用五个办法把这些内容移出 active window，但又不丢掉：

offload 大块工具结果：存进文件，context 里只留一段 preview。

summarize：接近阈值时做摘要，原文还能找回来。

skills 按需加载：用到时才放进 context。

交给 subagent：嘈杂的工作让 subagent 去做。

长期记忆写成 markdown 文件：由你自己掌控。

其中我觉得最惊喜的是offload 的做法是把这一大堆原样塞进柜子，也就是存成文件，桌上只留一张便签：这是什么、存在哪个文件、开头几行长什么样。之后真需要哪一段，agent 再用 read 或 grep 去文件里精确地取那一段回来，本质上我觉得就跟人的工作记忆差不多，因为人的工作记忆它的本身就很少

其他一些相对来说，目前工程上都有比较好的实践和比较好的案例了，但是这个工作记忆，我觉得很有意思，类似于以前的 hot.md，但是实际上解决的问题是不一样的，具体的区别：

Hot.md 是把少量关键信息常驻推进 context。offload 是把大块信息移出 context，只在需要时再拉回来。

Hot.md 放精炼的规则、偏好和进度，几百行以内。offload 放原始的、又长又杂的工具结果，比如日志、网页、搜索结果。

Hot.md 由人或 agent 精心维护，内容会反复改写。offload 由框架自动完成，原文只写一次、基本不改。

Hot.md 跨会话长期存在。offload 的文件多半只在这次任务里用，用完就可以丢

offload 在实现：

在工具调用层加一层 middleware：结果超过阈值（比如 20k tokens）就写进 /tmp/results/.md。

返回给模型的是一段 stub：文件路径、总长度、前 N 行或自动生成的摘要。

给 agent 配好 read_file(path, offset, limit) 和 grep 这类工具，让它按需分段读取。

可选：任务结束时清理这些文件，或者把有价值的结论提炼进 Hot.md 这类长期记忆。

相比较这个工具，我觉得它的实验思路尤其值得学习。它大概分为五步：

读取工具列表，拿到每个工具的名称。也拿到工具描述和参数 schema，这些才构成模型选择工具的输入

在此基础上出一些陷阱题。这些题不是简单题，而是针对每个工具，生成相邻工具的边界请求，专门用来测试模型会不会搞混

把整个工具列表和题目交给真实模型，记录它选了哪个工具，以及同一道题跑了多少次。因为模型的输出有随机性

最后汇总成一个混淆矩阵。表的行是正确答案，列是选的工具，一眼就能看出来哪些正确工具经常被误选成哪些其他工具

在此基础上对它进行计算，给出precision和recall，并且附带置信区间

我觉得这对于后面做evaluation来说，相对给了一些启发，怎么样刻意营造一些数据，然后得到一个更加逼真的precision和recall

### 主动型 Agent，先设计何时打扰和确认

> 2026-10-26 10:49:53 · `#claude-duet`

设计 approval moment，而不是更好的聊天窗：读、起草、准备可以自己做；发送、付款、签名、删除必须先给你看再等你点头

主动性设计，不一定要一天二十四小时持续运行；对我的设想来说，定时检查可能更划算，主要是① 定时巡检（晨间 brief + 白天周期检查）→ 用判断力筛「该不该打扰你」；② 你丢任务 → 上云端 VM／自带浏览器后台干，干完或要审批再通知

知道什么时候应该打断用户，这部分其实是所有的个人助手最重要的环节，Approval moment 一般不在「聊天里口头说一声」，而是一个可审、可改、可点头的动作卡片，卡在真正产生外部副作用之前

发送前：邮件／Slack／社媒——展示收件人、正文、附件，你改完再 Send

花钱前：购物、订阅、转账——展示商品／金额／支付方式，钱包或虚拟卡二次确认（Duet + Link 就是这种）

改状态前：删文件、改权限、签合同、发 job post——diff 或摘要 + Confirm

连新权限时：首次接 Gmail／日历，或 escalation 到更敏感 scope

工程做法：

风险分级：读＝自动；写草稿＝自动；外部 write／pay／delete＝必须人工。用策略表，不靠模型自觉。

统一 Action Proposal：{action, target, preview, reversible?, risk}，UI 只渲染这一种卡片（Duet 的「先给你看再等你」就是这层）。

Classifier / auto-mode：模型或独立分类器判定能否走自动；高风险强制打断（Claude Code／Duet 的 auto mode classifier 一路）。

幂等 + 可撤销：能 draft 就不 live send；能软删就不硬删；超时未批＝取消，不要默发。

会话外也能批：通知点进去只批这一张，不必回到长对话（proactive 场景刚需）。

审计日志：谁在何时批了什么，出事可回放

checklist：

列清所有 side-effect tools，标 auto / ask / never

每个 ask 必须有人话 preview（不要只丢 JSON）。

允许编辑后再批，避免「否决 → 重说一遍」

用 eval 测：该问的时候有没有问、不该烦的时候有没有乱弹

打扰预算：同类低风险可合并成一条「今日 3 封待发」，别每封都推

### Skills 和 Tools 的渐进式加载

> 2026-10-26 13:06:10

agent loop 中 skills & tools & mcp progressive disclosure思考

默认我们都知道Skills 是按 progressive disclosure 设计的——平时只暴露名字和一句简介；真正要用某个能力时，再把完整说明、schema 或代码拉进上下文，skills 是三层 progressive，平时只把 name + description 放进系统提示（大约每个一百来个 token），真正用到时，再读完整的 SKILL.md，最后需要时再拉引用文件或脚本（脚本多半直接跑，代码本身不一定进上下文）

我想谈一谈 MCP 和内置 tools，MCP 一般有 tools Search，若没开 Tool Search，工具的完整 schema 每轮都会占上下文。Claude Code 默认会开 tool search：先给一份精简目录，搜到再按需加载完整 schema。API 侧则要给工具标 defer_loading: true 才 defer

### 发上等愿，结中等缘，享下等福；择高处立，就平处坐

> 2026-10-09 01:27:27

发上等愿，结中等缘，享下等福；择高处立，就平处坐，向宽处行

「许上等愿，结中等缘，享下等福」讲的是对欲望的分层管理。

愿要上等：志向、格局定得高，想做的事要有分量，这决定你往哪走。

缘要中等：和人交往、找机会，不攀附也不将就，不去追逐顶级资源，保持平常心。

福要下等：享受只取最低一档，物质欲望放到最低。

「择高处翼，居中间坐，向宽处行」讲的是人在世上的位置和姿态。

站高处：看问题的视角、做人的标准要高，才能看得远。原文是「立」，截图里写成「翼」，也可以理解成从高处起飞。

坐中间（原文「就平处坐」）：日常待人处事放平、居中，不显摆、不走极端。这和儒家的中庸是同一个意思。

向宽处行：选路要选宽的。宽是心胸宽、退路宽、给别人留余地，不把自己逼进窄巷，也不把别人逼到墙角。

精神上取高，交往上取中，享受和姿态上取低

霍华德所处的世界依靠法律、声誉、职业伦理和社会关系去运作的。但是拉罗所处的世界是依靠暴力、利益、恐惧和权力运转的。他们在错误的时间、错误的地点相遇，就会形成一种错误的结果。

我觉得还有一点就是很有意思，就是关于间接影响这个点。其实间接影响案例有很多，就是比如说，举个我们每个人都会有感同身受的，就是我们很多的性格可能往往蕴含着就是从小到大某一些性格的转移。比如说，一个孩子从小到大，如果他的父母是有暴力倾向的话，这个孩子他在长大之后的可能更难建立安全感，但并不意味着他注定不能拥有稳定的人格。可能也会引发出来其他的一些现象。就比如说对待下属，管控很严格。可能从小到大，如果缺少安全感的话，可能会把这个安全感也会传递给自己身边的人

### 越轨和标签理论

> 2026-10-24 23:05:58 · `#心灵猎人`

越轨理论讨论“什么行为会被视为偏离规范”，标签理论进一步追问“谁有权作出这种判断，以及被贴标签后，人会怎样改变”

越轨本身是超过规矩，社会学中的越轨，是偏离某个群体或社会规范的行为。它不一定违法，也不一定有害，例如，在强调服从的组织里，公开质疑上级可能被视为越轨，但是实际上另一些社区却可能鼓励这种行为

这里想到的是霍华德·贝克尔的社会学著作[《局外人》（Outsiders）](https://www.simonandschuster.com/books/Outsiders/Howard-S-Becker/9781982106225)，不是加缪的小说。群体制定规则，再把规则应用到某些人身上，将他们认定为“局外人”

标签的作用，由此可能同时发生在两处：别人怎样对待他，以及他怎样理解自己。 即使他不认同标签，别人对他的排斥也可能改变他的处境

一次行为 → 被认定为某种人 → 被区别对待 → 机会与关系发生变化 → 后续行为受到影响

这个过程说明，行为本身与“被认定为越轨者”需要分开看

### sandbox 首先是涉及到执行啊

> 2026-10-04 00:04:33

sandbox 首先是涉及到执行啊，首先是在电脑的环境中，那么就是本质上是有不可信的执行在电脑上所以才需要

所以如果数据库 CRUD 已经由受控后端执行，通常不必再为每次结构化调用分配独立的代码执行沙箱

读取 S3 的文件也不需要 sandbox，前提是它们确实是后端代你执行的结构化 tools， 很明显的特征是参数是可以校验的，权限是可以控制到具体的行和用户的

另外即使是纯粹就是文件读写，其实也不需要sandbox，无非就是给一些read file、write file，这两个tools，后端直接读取用户前缀和 CRUD 没区别，关键是有没有 bash

那么需要 sandbox 的情况，就是跑 shell，比如说，执行模型写的代码，装一些依赖，然后开一个浏览器，再比如说 GREP、sed 这类命令处理一堆文件的时候，这时候是需要的到一个执行环境

如果是一些高频行为，就一定要做成结构化的tools。因为实际上，哪怕sandbox可以做，也完全没有必要；为了速度更快，更精准，也不要让它跨一些权限

不另开执行沙箱，不等于可以省掉鉴权、输入校验、数据隔离和审计。这里区分的是执行方式，不是要不要安全边界。

### 对 superpowers 的判断

> 2026-10-05 16:55:21

superpowers 可谓工程界最火方法论

GitHub 近 30 万 star ，现在 v6.4.2 版本

作者说 v6 在他自己的评测里构建速度快了大约 50%、成本低了大约 60%

我之前一直在用 brainstorming 的部分，会让你开始不断的和你确认澄清需求，避免 LLM long time coding 发生偏离

然后还有就是他们的拆分工作单元、用隔离的 worktree 并行开发，这在长任务和多 agent 并行时尤其重要

以及我也用它把自己的一些标准沉淀为一些可以复用的工作流，比如说 TDD、代码 review 规则

还有就比如说systematic-debugging 和 writing-skills怎么样系统化的排查问题，以及如何写自己的 skills

其实随着模型的能力提升brainstorming可以降低，brainstorming 比原生的 plan mode 我觉得是好用的，但是如果简单的任务都走 brainstorming 挺消耗token 和时间的

我一般小任务不会用 brainstorming ，，然后同时使用精简版 writing-plans、systematic-debugging

只在大任务时开：subagent-driven-development、TDD、代码审查这一串

因为平常是多电脑开发， 我一般是 linear 做任务队列的

主电脑和 AI 对齐，跑 brainstorming 和 writing-plans，子电脑负责"做"，只跑执行、TDD 和验证

用 brainstorming 把需求问清楚，再用 writing-plans 拆成独立的工作单元。每个单元要能单独完成、单独验证，不互相依赖；有依赖的就在 Linear 里标 blocked by。

每个单元写成一张 Linear issue，描述用固定模板：

目标：一句话。

范围：允许改哪些文件或目录，禁止碰哪些。

验收标准：可执行的检查，比如哪些测试要通过、命令输出什么。

上下文：相关文件路径、计划文档链接。

执行模式：tdd 或 quick。

打上 agent-ready 标签，表示可以领取。

子电脑（执行者）

只装执行相关的 skill：executing-plans、test-driven-development、systematic-debugging、verification-before-completion。brainstorming 要关掉，不然它会反过来问问题，没法"无脑执行"。

每张 issue 用独立的 git worktree 和分支，分支名对应 issue 号，比如 xw-123，这样多台机器并行也不会冲突。

执行流程：领取 issue，状态改成 In Progress，按验收标准做，自检通过后提 PR，PR 链接回填到 Linear，状态改成 In Review。

遇到卡住或需要决策的情况，不要猜：在 issue 里留评论说明卡在哪，打上 needs-human 标签，然后去领下一张

主电脑用 code-review skill 审 PR，对照 issue 里的验收标准检查。通过就合并，issue 关闭；不通过就在 issue 里写清楚要改什么，重新打回 agent-ready

### Design.md 的定义我觉得尤其重要

> 2026-10-16 16:59:42

Design.md 的定义我觉得尤其重要，我一般开始会去 https://github.com/VoltAgent/awesome-design-md 上找一些好的有品味的网页，然后定义，微调
主要是包含三种类型的内容：
1. 基础变量（design tokens）

颜色： 主色、辅助色、背景、文字、边框，以及成功、警告、错误这类状态色，最好同时给出亮色和暗色两套。

字体： 标题和正文分别用什么字体，字号阶梯（比如 12/14/16/20/32/48），行高和字重。

间距： 一套固定的间距刻度，比如 4 或 8 的倍数

圆角、阴影、边框： 各用几档

动效： 动画时长和缓动曲线，比如快 150ms、慢 300ms

布局： 栅格、最大内容宽度，手机、平板、电脑的断点

2. 组件规范

按钮、输入框、卡片、导航、弹窗这些常用组件，各有哪几种样式（主要、次要、幽灵按钮），有哪些状态（默认、悬停、按下、禁用、加载），以及该在什么时候用

3. 风格原则（这层最能体现品味，也最常被漏掉）

气质： 用几个形容词定调，比如"安静、纸感、克制"。

该做和不该做： 比如不用渐变、不用纯黑、每屏只放一个强调色

图像和插画： 用什么风格，比如真实照片还是手绘插画

文案语气： 用什么口吻说话

无障碍： 对比度达标，键盘能操作

给 AI 用时，第 3 层最关键：写清"不要什么"，比只写"要什么"更能避免 AI 默认的那种紫色渐变风
比如说不要有过多的口水话

### 能力、位置与沉没成本

超越享乐主义通常是在说：快乐很重要，但它未必足以定义一种值得过的生活。 人还可能看重真实、关系、自由、创造，以及成为自己认可的那种人

“这件事让我开心吗？”仍然值得问。
