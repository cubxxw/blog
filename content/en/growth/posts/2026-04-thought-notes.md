### First, they refactored the repo from a monolith

> 2026-04-04 16:39:18 · `#格物/ai`

First, after they refactored the repo from a monolith into multiple independent crates, compile wait times dropped sharply and throughput multiplied several times over. This means the repo structure optimized for agents may not be the same as the repo structure optimized for humans. A human can wait 30 seconds for a compile; hundreds of agents compiling at once — hundreds of 30 seconds — is a catastrophic I/O bottleneck

In multi-agent architecture, a point you absolutely must think about is how to avoid catastrophic I/O bottlenecks

Because if 100 agents are working at the same time, each one has to compile once, and each compile takes 30 s, that's a system-level disaster — the system just locks up / compile time rises exponentially

If it's split into multiple crates, when an agent modifies module A it only compiles module A, compile time is lower, and it avoids a concentrated compile explosion

Repo structure optimized for agents ≠ repo structure optimized for humans

Fine compile granularity

Concurrency friendly

High cache hit rate

Scattered I/O

### Agent Teams

> 2026-04-06 21:11:54 · `#格物/ai`

Subagents are like "interns sent out on errands" — they receive a focused task, finish it, and return a result. The main agent always holds control; the Subagent doesn't need to communicate with anyone else. Agent Teams is more like forming a project group: each member is responsible for their own part, but they stay in communication the whole time. When the backend developer changes the data model, the frontend developer knows immediately, rather than only finding out when integration tests fail

Subagents = Delegation, Agent Teams = Collaboration

How to choose between them? The core criterion is: do the Workers need to communicate with each other? If the work is independent of each other (like a backend audit, a frontend audit, and a test coverage check each happening separately), use Subagents. If the Workers need to challenge, review, or build on each other's output (like one Teammate writing an API spec, another reviewing it and flagging inconsistencies, and a third writing the corresponding tests), use Agent Teams

Generally speaking, there's only one scenario that needs Agent Teams

which is when multiple agents need to play different roles and review each other's output

### Analysis of quantification methods

> 2026-04-08 15:46:30 · `#格物/ai`

Dimensional decomposition + Few-shot calibration

One is to take a complex problem or a vague problem and split it into N sub-questions that can be answered independently, each with a clear pass or fail condition. Then weight the dimensions to get an appropriate score

Compared with comparative ranking, I think rather than giving an absolute score, it's better to ask which of A and B is better. For humans — and including model judgment — judging relative quality is much more stable than giving absolute scores. Like using this image or another image and comparing them — that's also a method; let it keep cycling through this way of training, until it can collide with something with a relatively high contrast

And there's actually another very important thing: including when we write Claude, we don't list what's good; instead we list what's bad. Because hitting a deduction has a far higher hit rate than hitting a bonus

Then there's measuring through some mechanically measurable behavior, like using Playwright to click the UI and test API endpoints, then checking the screen state. That's more precise than you saying whether usability is good or not, and it's also easier for an LLM to solve

Then there's giving some Few-shot anchoring — this means calibrating with examples that have detailed score breakdowns, aligning with humans' own preferences, to reduce scoring drift. Not just telling the model to score 1–5, but why this case is a 3 or a 4 rather than a 5

Is this design beautiful?" is hard to answer consistently, but "does this follow our principles for good design?" gives Claude something concrete to grade against.

What quantification's method is doing isn't measuring "true quality," but measuring "the degree of alignment with some set of principles." So whether a quantification method is good ultimately depends on whether your principle set actually captures what you want

### Measurement is essentially relative too. When we read about relativity

> 2026-04-08 17:45:37 · `#格物/ai`

I think measurement is essentially relative too. When we read about relativity, apart from the speed of light, all other standards of measure — like speed, why time speeds up, and who is moving and who isn't — are relative. There's a frame of reference to measure whether this object has shifted in the real world. And especially, some shift values may depend on human preferences, culture, and situational needs

The principle set can go wrong at three levels:

Incompleteness — your principles don't cover what you actually care about
 The article's four design dimensions missed "emotional resonance" — a design can meet all four dimensions and still leave the user feeling nothing. This dimension is hard to operationalize, so it was omitted. Omission doesn't mean it isn't important, only that it isn't measured.

Faulty proxy — the thing you measure is a proxy for the thing you actually want, but proxies distort
 Goodhart's Law applies precisely here: when a measurement becomes a target, it ceases to be a good measurement. The evaluator in the article was trained to penalize "purple gradient on a white card," so the generator learned to avoid that feature — but that doesn't equal genuine originality, it just means that particular signal of originality failure is gone.

Evaluator drift — the principle set itself encodes the evaluator's preferences, not the user's
 The article's author wrote: "The wording of the criteria steered the generator in ways I didn't fully anticipate." The principle set included wording like "museum quality," and as a result all output converged toward museum aesthetics. That's the evaluator's taste, not the user's need.

A common misconception is: if the principle set has problems, just keep refining the principle set until it perfectly captures reality — but this path generally doesn't work, and the reasons are:

True intent is itself fluid. You can't capture a dynamic preference system with a static principle set. The design you think is good today may feel outdated six months later. Your principles at this moment are the sediment of your experience up to the last moment

Operationalization itself is a form of lossy compression. Turning "emotional resonance" into a scoreable metric necessarily requires trade-offs and simplification. This isn't a technical problem; it's a limit of language and concepts themselves

The evaluation system shapes what is evaluated. The Generator isn't just being measured — it changes during the process of being measured, converging in the direction the principle set defines, and simultaneously moving away from the space of possibilities the principle set doesn't cover

In the end this can't be solved, only managed

### The bet of building a product: users need a complete experience, you win on execution

> 2026-04-13 12:42:18 · `#格物/ai`

The bet of building a product is: users need a complete experience, and you win on execution, taste, distribution

The bet of building a protocol is: the endgame of competition in the agent era is interoperability, and you win on the right to set the standard

Settle which kinds of tasks suit full automation (task-boundary protocol)

The moat should be that the protocol you define yourself is depended on by other agents, and your execution framework is adopted by more downstream tools
