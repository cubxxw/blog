### OpenClaw Skills Loading: The Four-Layer Decision-Filtering Mechanism

> 2026-03-03 16:57:42 · `#格物/ai`

OpenClaw's skills-loading principles.

The LLM is never the "full-set indexer" of skills.

It's only the "decision-maker for the final candidate set."

Skills decisions are layered — usually four layers of filtering.

Layer 0: Skill Registry (system layer), stored in a database, vector store, or index.

Layer 1: non-LLM routing (hard filtering), based on certain types, embeddings, then abstracted out.

Layer 2: Candidate Skills (the set visible to the model) — this is what finally gets inserted, maybe a few, a dozen, twenty-odd skills, with name, description and schema.

Layer 3: invocation & execution (runtime) — usually only 0–1 are invoked, returning the result for that turn.

### OpenClaw's cron Mechanism: Time-Triggered vs Event-Triggered Division of Labour

> 2026-03-04 13:57:03 · `#OpenClaw`

The cron in openclaw feels quite interesting

You can set temporary tasks, and also recurring tasks

The difference between sub-agent and cron is really like this: the openclaw gateway is like a company, cron is the alarm clock, and sub-agent is like a temp outsourced worker brought in on short notice

Trigger dimension: cron is triggered by time, whether it's a one-off task or a periodic task

A sub-agent is triggered by events and instructions, usually dynamically spawned by the main agent (or a cron task) deciding "this job is too time-consuming, I'd get stuck doing it myself"

cron solves when to do it; sub-agent solves how to outsource and break down a big task

A Sub-agent is throwaway when done; a Cron task is static and persistent (its config is saved in the .openclaw/cron/ directory), and stays around long term unless you clear it manually

Under the hood, openclaw doesn't rely on the underlying operating system's crontab, but maintains a cron scheduler inside the nodejs gateway

In order not to interrupt the context of your current chat with the main Agent, when Cron is woken it usually spins up an "independent session" and runs the task silently in the background. Only when "deliver": true is set in the config file will it send the final result to your Telegram, WhatsApp or terminal

A Sub-agent is essentially a sandboxed, asynchronous, isolated environment, making use of OpenClaw's sessions_spawn mechanism

When the main Agent judges a task is heavy, it calls the system-level built-in tool sessions_spawn. This call is non-blocking: the main Agent throws out the task and can keep chatting with you

openclaw creates a brand-new Session for the sub agent; it doesn't inherit the hundreds of rounds of messy chat history from the main session, and only injects a clean toolset (such as TOOLS.md) as needed

The sub-agent and the main process each run in different parallel streams (if the highest security mode is enabled, the sub-agent even runs in a separate Docker container). When the sub-agent finishes, it packages the result into a standardised internal event block (Announce Context) and, like sending a network request, "calls back" and pushes the result into the main thread or chat channel that created it

### launchd vs systemd: Two Philosophies of Service Management, Event-Driven and State-Driven

> 2026-03-04 14:09:51 · `#格物/mac`

Thinking about the differences between macOS's launchd and systemctl

Actually launchd : systemd   =  macOS's philosophy of service management : Linux's philosophy of service management

They solve the same problem, but the approaches they take are diametrically opposed

Their functionality is almost the same: user level, system service management, restart on failure, scheduled triggers

The design philosophy: one is event-driven, the other command-driven

launchd is event-driven; not always running saves power, it wakes fast, it's aimed at desktop users, with strong consistency

Linux's systemd is state + dependency driven, including active / failed / inactive, leaning more towards long-running services and service stability

In other words, with launchd the system decides according to rules when things may run

User-level launchd is desktop-friendly

### Introduction to the secrets directory

> 2026-03-04 17:25:25 · `#OpenClaw`

This directory is mainly used to store all the high-privilege credentials an AI agent needs to run autonomously:

LLM API keys: call keys for providers such as OpenAI, Anthropic, xAI (Grok).

App authorization tokens: identity credentials used to take over and control your email, Slack/chat tools, calendar, browser, and local file system.

Environment variables: sensitive configuration parameters needed for the system and each sub-agent (Agents) to run

When the Clawdbot Gateway service starts, it reads the configuration files in this directory (such as clawdbot.json or a .env file). The system loads these tokens and keys into memory and, depending on the needs of different tasks, assigns them to different sub-agents (for example: the highest-privilege Main Agent, a permission-restricted Work Agent, or a sandboxed Coding Agent)

When the AI decides to call a tool (like batch-replying to emails or operating on a local code repository), it first checks the permission whitelist (usually in exec-approvals.json at the same level). Once verified, the system pulls the corresponding credentials from the Secrets directory and dynamically injects them into the execution environment (a Docker sandbox by default), or sends them as HTTP headers to a third-party service's API

To ensure the AI agent can run autonomously in the background for a long time without constantly asking the user for verification codes or passwords, the system stores all authorization state persistently in this directory, working together with memory files like USER.md (information about you) and SOUL.md (the AI's personality settings)

### The sessions_spawn mechanism

> 2026-03-04 17:28:47 · `#OpenClaw`

sessions_spawn is a built-in system-level tool (Tool) that OpenClaw provides to the main Agent. When the main Agent hits a heavy task (say it needs to search dozens of web pages, or run a long code-test process), it can call this tool to dynamically "clone" or spawn multiple sub-agents to work in parallel in the background

A sub-agent doesn't inherit the hundreds of rounds of idle chat between you and the main Agent. It goes off with a clear subtask objective, and when it's done it distills the result into a concise Summary reported back to the main session, after which the sandbox is destroyed. That way your main chat interface stays clean forever

Cost optimization, the high-level feature geeks love most: through the model parameter of sessions_spawn, you can achieve heterogeneous model collaboration

Your main session might be running the smart but expensive Claude 3.5 Sonnet or GPT-4o, dedicated to understanding your complex intent and breaking task structures down

Calls to sessions_spawn are non-blocking

### Ralph Loop's Context Management, a Deep Dive

> 2026-03-09 16:36:54 · `#格物/ralph`

First you have to understand the essence of the problem, Context Rot

Traditional AI coding sessions face what's called "context rot": every prompt, reply and correction keeps accumulating tokens in the context window; wrong implementation approaches remain in the history, and even if they get corrected later, they still influence subsequent output

The compaction loop is essentially about constantly compressing the conversation to free up space for context, but the more you compress the less work gets done, until finally you fall into an infinite loop

It's very common in MCP scenarios, including MCP tool definitions being too long, tool results being too large, too many parallel tool calls, and very long system prompts, rule files, CLAUDE.md

compaction  loop = context too full → triggers compression → still too full after compression → compress again → repeat infinitely, the task can't move forward

As the number of tokens an LLM receives increases, the relationships between tokens grow quadratically (quadratic scaling). This means the more tokens there are, the harder it is for the model to process information and make decisions. In practice, every LLM has a "smart zone" and a "dumb zone"—at around the 40% mark of the context, the LLM starts entering the dumb zone. The exact boundary varies from person to person, but there's no doubt that a boundary exists

Compaction is a lossy function. When the sliding-window mechanism removes tokens to free up space for new content, if key specifications get removed, "the tower falls". This leads to the dumb zone—after exceeding 60-70% of capacity, LLM performance degrades measurably

Research shows the dumb zone isn't only a function of the token limit, but also of context pollution. Even if the window isn't full, the presence of contradictory information (for example a bug and its failed fix attempt) also confuses the model's probabilistic generation

Geoffrey Huntley condensed his design philosophy into one sentence:

"Ralph is a deliberate attempt to minimize allocation. So I never get a compaction event."

The core insight is to use a fresh context on each iteration. Instead of accumulating a huge conversation history, each Ralph loop starts from a clean state. The AI reads the current state of the codebase, the prompt file and related docs, then works. Progress gets committed to git. The next iteration starts from a fresh state, reads the updated state, and carries on

Ralph's design sidesteps compaction by re-allocating the full specification on every iteration, ensuring key context is never compressed away

Ralph Loop doesn't try to "summarise" the past; instead it guides the Agent to reload itself through the prompt. Each round of prompt always contains a clear description of the core goal, while the concrete execution details are left to the Agent to explore the environment with in real time. This "just-in-time context" loading method allows Ralph to handle projects far larger than a single context window's capacity

> 2026-03-09 16:53:51 · `#格物/AI`

### OpenClaw's session management method

> 2026-03-10 17:32:43 · `#格物/openclaw`

The Gateway centrally holds state + sessionKey routing + sessionId continuation/reset + transcript persistence + compaction

The gateway is the single source of truth. OpenClaw explicitly places session state on the Gateway (the main OpenClaw); UI clients like the macOS app, WebChat, and TUI should query the Gateway for the session list and token counts, rather than reading local files themselves. In remote mode, the files you see on your own machine aren't necessarily the session state actually in use — what's really in effect is the store on the remote Gateway host

So the architectural orientation is centralised state, with multiple UIs sharing the same session truth, and the front end as stateless / weakly stateful as possible

Multi-device consistency is very important, otherwise web, desktop, and chat channels easily end up each having their own history

OpenClaw's session persistence is split into two layers:

The first layer is sessions.json, a small mutable mapping of sessionKey -> SessionEntry, holding the current session metadata

The second layer is the .jsonl transcript, the real conversation stream, using append-only JSONL, in which messages, tool calls, compaction summaries, and so on are stored, used to rebuild the model context in subsequent turns

One important reason OpenClaw's long sessions can keep running is compaction. It summarises earlier conversation into a persisted compaction entry while keeping the newer messages; subsequent turns see "compressed summary + recent messages." And this compaction is persistent — it isn't a one-off summarise that gets thrown away

### The Relationship Between People and Agents, and Between Agents and Agents

> 2026-03-20 13:51:45 · `#格物/ai`

It could be the shape of a product like Routa

But I think at the user layer, around a product, users may have a shape they lean toward more

What users really care about isn't "I'm using an agent," it's "my goal is moving forward"

When agent capability is strong enough, the relationship between user and product rises from task level to goal level. For example

Now: user opens the app → does one operation → completes one task

Future: user expresses an intent/goal → the product (containing the agent) keeps pushing it forward → the user only steps in at key nodes

Continuously advancing a bounded goal is naturally the shape of a project

There are several categories; among them, the one that Another naturally lands on doesn't feel like a task-granularity assistant, but a goal-granularity companion

What the product remembers is "what I'm doing"; it can understand a goal across time and across sessions, and for different users it may take different shapes—it could be a project, or it could be called "my goal," "my plan," "my journey"

The most fundamental change in the AI era isn't "efficiency improvement," it's that the friction between a person and their goal disappears

In the past, when a person executed a goal there was a huge amount of "execution tax" in between—looking up material, writing documents, coordinating, repeated operations... this friction consumed not just time, but attention and willpower. Many goals die in the friction; it's not that the person doesn't want to do it, it's that while doing it, it breaks off

Once the agent cuts this layer of friction sharply, the bottleneck shifts from "can it be executed" to "do you want it"

Here a project is essentially an interface between a person and their own intent

People's sense of their own goals is actually fuzzy, drifting, and even self-deceiving. A good project shape, if the agent understands you well enough, is actually helping you do one thing: make your implicit intent explicit, and then keep it in focus

This is why I think the direction of Another Self is more interesting than an efficiency tool—an efficiency tool assumes a person knows what they want and just needs help executing. But the reality is that people often aren't clear about what they really want, or they're clear but don't dare admit it

AI will push people's attention back to the most essential question: what do I actually want, what am I living for

The essence of relationship

Between a person and an agent, there are essentially three layers of tension:

Intent layer: what do I want, how much does the agent understand, is the understanding correct. Control layer: when do I have the final say, when does the agent decide autonomously, where's the boundary. Trust layer: how much do I dare let go, what do I do if the agent makes a mistake, where does responsibility lie

Between agent and agent, it's essentially: division of labour layer: who does what, how to split. Coordination layer: how conflicts are resolved, how information is synced. Emergence layer: multiple agents collaborating will produce behaviour a single agent doesn't have, how is that managed

As a shape, a project mainly handles the intent layer and the division-of-labour layer—it provides a boundary container. But it is naturally weak in handling the control layer, trust layer and coordination layer

As a concept for human organisation and management, Project's implicit assumptions are:

goals are relatively stable

executors are predictable

time is linear

But the reality of agent systems is:

goals drift and evolve during execution

agent behaviour has uncertainty; it isn't an employee

multiple agents are concurrent, time isn't linear

So as a shape, project handles a mapping of human organisational problems, not an agent-native problem. It's a transitional shape, not the end state

> 2026-03-18 15:26:32 · `#格物/吴哥窟`

It lays out the Hindu, and later Buddhist, view of the cosmos.

Angkor Wat's cosmology is the core key to understanding the whole complex. In the Khmer civilization's worldview, the cosmos has a fixed structural model, and Angkor Wat is the material reproduction of that cosmos.

Mount Meru: the center of the cosmos and the gods. In myth, Mount Meru is the center of the universe (the world axis) and the dwelling place of the gods. The five progressively taller stone towers arranged in a "quincunx" at the center of Angkor Wat are precisely meant to reproduce the five peaks of Mount Meru. Through the corridors and towers rising level by level, the architecture symbolizes the pilgrim's arduous climb toward the realm of the gods. By reproducing the sacred Mount Meru on earth, Angkor Wat anchored the Khmer kingdom at the center of cosmic order, and established the legitimacy of the king who built it as a sacred mediator between gods and mortals.

Cosmic Ocean: the boundary between the sacred and the profane. Angkor Wat's outer perimeter is surrounded by massive stone walls and a moat up to 190 meters wide. These outer walls and moat were not merely fortifications or waterworks; they symbolize the ranges of mountains and the vast "cosmic ocean" encircling Mount Meru. On the spiritual level, the water reinforces the boundary of sacred space: when a pilgrim crosses the moat, it marks their crossing of the "cosmic waters," completing the inner transition from the mortal, profane world into the sacred center of the cosmos.

Echoing the myth of the "Churning of the Ocean of Milk." The symbolic meaning of the cosmic ocean is also tightly linked to the most famous giant relief at Angkor Wat, the "Churning of the Ocean of Milk." That myth tells of gods (Devas) and demons (Asuras) cooperating to churn the cosmic ocean in order to obtain the nectar of immortality. In this grand architectural context, the moat surrounding Angkor Wat is seen as the incarnation of the "ocean of milk," while the temple at the center represents the sacred cosmic order. This combination of water and architecture vividly expresses the Khmer belief about creating life out of chaos and maintaining cosmic balance.

- Long-term: China (87), South Korea, Japan (future returns, thrift)

- Indulgence: Mexico, the US (68), Australia (enjoying freedom)

### The core differences between Theravada and Mahayana Buddhism

> 2026-03-14 22:50:06 · `#佛学`

A rough comparison: practices vary considerably by region and monastery, so the following should not be read as universal rules for either tradition.

In terms of thought, Theravada emphasises individual practice, pursuing the fruit of arhatship and strictly following the Pali Canon; Mahayana (Mahāyāna) emphasises saving all beings, pursuing the bodhisattva path and Buddhahood, with a far larger scriptural system (Prajñā, Lotus, Avatamsaka, and so on)

In terms of architecture, the core of Theravada is the stupa (stupa), usually a solid structure in the shape of a dome or a bell, with a golden spire, which cannot be entered; the faithful circumambulate it in worship. Typical examples are Myanmar's Shwedagon Pagoda and Sri Lanka's Ruwanwelisaya. Thai stupas evolved into the tapering "reliquary" (Chedi) form

The core building of Mahayana is the hall, emphasising that the faithful can enter it to worship the Buddha. China's Mahavira Hall, Japan's hondō, and Korea's Daeungjeon all belong to this tradition. In the Mahayana system the pagoda gradually retreated from the centre to an auxiliary position (such as China's multi-storey pavilion pagodas and Japan's five-storey pagoda), becoming part of the temple's scenery rather than its centre

Theravada temple layouts are relatively loose and open, with the stupa as the visual centre and monks' dwellings (Kuti), ordination halls (Sīmā), and preaching halls (Vihāra) scattered around. The overall feeling is closer to a monastic living community

But China's Mahayana temples go in for axial symmetry, advancing layer by layer, with clear hierarchy

Theravada halls generally focus on Shakyamuni Buddha, which does not mean they contain only one image, with postures mainly of meditation, the earth-touching gesture subduing Mara, and the reclining nirvana Buddha, in a style that is simple and restrained

Mahayana halls commonly have many Buddhas and bodhisattvas together — the Buddhas of the Three Times, Amitabha, Medicine Buddha, Guanyin, Manjushri, Samantabhadra, and so on, sometimes also groups of arhats. The iconographic system is vast, reflecting Mahayana's rich faith in Buddhas and bodhisattvas

### Chinese-Japanese Love Semantics: Chinese Relationship Positioning vs. Japanese Emotional Granularity

> 2026-03-01 15:15:41 · `#格物/爱`

Chinese-Japanese characters * Love

Differentiated distinctions (of course, the main reason for differentiation is social and cultural differences).

Chinese "love" focuses more on precise positioning of relationship attributes; Japanese "love" focuses more on subtle division of inner emotional stages and states.

For example, modern Chinese "爱" is a highly condensed broad-term. Whether romantic passion (corresponding to Japanese "koi") or deep bonds (corresponding to Japanese "ai"), Chinese at the root of nouns and verbs uniformly calls it "love." We use "爱情" "谈恋爱" to cover the entire process.

Japanese "dual-track system" (koi vs. ai): A common explanation draws a distinction between "恋 (こい-Koi)" and "愛 (あい-Ai)" when describing love.

- **Koi**: Focuses on longing, desire, passion, romance—usually refers to the impulse and yearning in early love stages of "wanting to get the other person" (often with self-centered color).

- **Ai**: Focuses on giving, tolerance, persistence, selflessness—usually refers to deep bonds after relationship stabilization, can also be used for family love, great love.

- Therefore, Japanese has "恋人" (in romantic passion phase) and "愛人" (in Japanese usually refers to extramarital affair partner, but literal original meaning is deeply loved person, later semantic shifted).

Also, when Japanese express love, vocabulary precision more reflects subtle emotion capture:

- **Suki**: Like—in Japanese daily life, expressing love rarely directly uses "Aishiteru," but uses "Suki" or "Daisuki." This reflects Japanese culture's "sense of distance" avoiding emotional weight pressing on the other.

- **Koishii**: Accurately describes a "strong longing and attachment due to not being by side"—not limited to people, can also be for hometown, old objects.

- **Itooshii**: Accurately describes "looking at the other feeling very cute, heart-aching, wanting to tightly embrace and protect."

- **Amaeru**: Describes an interactive state of "using the other's love for oneself, showing dependence, acting spoiled to obtain emotional comfort." (Psychology master Takeo Doi specially researched this word, considering it the core of Japanese culture.)

“The moon is beautiful tonight” (月が綺麗ですね) is often used as an example of an indirect expression of affection. I have not verified a reliable source for the story that Natsume Soseki translated “I love you” this way.

Abstract Ladder.

Core idea: how to consciously switch back and forth between different abstract levels to better understand and design complex systems.

This "ladder of abstraction" isn't just a language theory—it's a thinking methodology, emphasizing dynamic back-and-forth between abstract + concrete ↔ abstract.

Keeping the car in the center of the lane actually advocates three basic actions:

Control parameters—only by keeping variables within controllable ranges can you naturally explore.

Rise to abstraction—look beyond one concrete instance, but creating an abstract representation that can represent all instances.

Return to concreteness—looking at abstract diagrams is cool, but doesn't explain detailed reasons; need to select a concrete instance to inspect.

So it's back and forth: up-abstract → down-details → re-up-abstract → ...

Just like analyzing a place's culture and people: observe → practice → understand → observe.

Ladder meaning:

- **Bottom**: At start we can only see concrete situations—like a car's position at a certain moment.

- **Middle (first abstraction)**: Abstract away concrete variables, get broader overview.

- **Higher**: Simultaneously abstract more dimensions—like formatting data on all parameters, highly generalized overall pattern.

Abstract ladder is essentially a cognitive hierarchy—and not just using high-level thinking is enough, but need to flexibly convert between levels to have both height and depth.

- Staying purely concrete → easy to get trapped in details, can't see overall trends.

- Staying purely highly abstract → lose intuition and causal connections.

- Switching back and forth → can discover patterns and explain reasons. This is precisely the key to deep understanding.

Actually, translating to cognition vs. action distinction, this analogy also holds: thinking resolves action uncertainty, action resolves thinking uncertainty—the two are complementary, mutually fulfilling.
