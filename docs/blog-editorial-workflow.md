# Blog Editorial Workflow

这份协议只负责把上游 brief 变成 `cubxxw.com` 的博客文章。选题形成、作者长期定位和其他平台分发不属于当前仓库。

## 总流程

```text
brain 下发 brief
  → 队列扫描与认领
  → 站内查重
  → 材料与缺口梳理
  → 外部研究 + 搜索意图研究
  → 中文原生写作
  → 逻辑与证据审读
  → 作者声音与 AI 味审读
  → SEO/GEO + 内链
  → 封面
  → 评分与确定性检查
  → ready-to-publish
  → 作者签字后发布
```

每次只处理一个 brief。高产不是目标；brief 没有达到写作条件时，正确结果是 `blocked`。

## 1. 扫描与认领

运行：

```bash
npm run briefs:next
```

选择顺序：

1. `priority: high`；
2. `priority: normal`；
3. `priority: low`；
4. 同级按 `dispatched_at` 从早到晚。

认领前检查目标文件是否已经存在，以及站内是否已有同一搜索意图或同一核心判断。重复内容优先更新旧文或改成系列补篇。

认领时把状态改为 `claimed`。如果缺少以下任一内容，改为 `blocked` 并写清问题：

- 唯一命题；
- 作者一手增量；
- 允许公开的素材包；
- 隐私边界；
- 关键经历是否真实发生的确认。

## 2. 先整理研究问题，不直接写正文

把 brief 整理成四张小表：

### 命题表

- 文章要回答什么；
- 当前答案是什么；
- 最强反方是什么；
- 什么证据会让结论改变；
- 结论适用于什么条件。

### 材料表

- 已确认事实；
- 作者记忆；
- 作者观察；
- 待验证推论；
- 禁止使用的信息。

### 缺口表

- 需要作者补充；
- 可以通过站内材料解决；
- 可以通过公开研究解决；
- 当前无法解决但可以诚实保留。

### 文章增量表

- 读者从公开搜索结果已经能知道什么；
- 本文新增了什么经历、证据、解释或判断；
- 删除作者一手材料后，文章是否仍然成立。

最后一项如果答案是“完全成立”，说明文章已经退化成公开资料综述。除非 brief 明确要求研究型分析，否则暂停成文。

## 3. 外部研究分成两条线

### A. 认识碰撞

目标是检验文章，而不是给既定观点寻找装饰性引用。

至少主动寻找：

- 支持核心命题的证据；
- 最强反方或替代解释；
- 会限制结论适用范围的案例；
- 近年是否出现改变判断的新事实。

技术与产品事实优先使用官方文档、原始论文、标准、代码仓库和公司一手公告。二手文章可以帮助发现线索，但不能在存在一手来源时充当最终证据。

每条来源记录：

```text
来源 → 支持/反驳哪一步 → 能证明什么 → 不能证明什么 → 核验日期
```

引用数量没有最低要求。一个准确的一手来源胜过十个互相转载的链接。

### B. 搜索意图研究

目标是让需要这篇文章的人找到它，不是让关键词决定作者观点。

研究：

- 读者可能用什么完整问题搜索；
- 搜索结果主要在回答教程、定义、比较还是决策；
- 现有结果遗漏了什么；
- 本站是否已有可承接的相关文章；
- 标题和 description 能否准确兑现搜索承诺。

如果搜索需求很弱，但文章具有长期作者价值，仍然可以发布。此时采用“准确可发现”的标题，不为了流量改造成另一篇文章。

SEO 研究必须发生在命题确认之后。研究结果可以改变标题、结构和解释顺序；若要改变核心命题，退回上游重新确认。

## 4. 中文原生写作

先完成中文，再决定是否制作英文版。正文按以下顺序写：

1. **论证稿**：只保证问题、证据、推导、反方和边界完整；
2. **在场稿**：补回真实场景、行动、选择、代价和认知变化；
3. **阅读稿**：处理节奏、小标题、过渡和删减。

每个抽象判断附近至少有一项：

- 作者亲历；
- 可核验证据；
- 清晰推导；
- 明确的限定条件。

删除换一个作者也能原样成立的自我介绍、空泛时代判断、重复总结和为了显得全面而添加的工具清单。

## 5. 两次独立审读

起草者不能在同一遍里完成自我批准。至少分成两个独立上下文或角色。

### 审读一：逻辑与证据

检查：

- 事实、作者观察和文章推论是否混淆；
- 是否把相关性写成因果；
- 引用是否真的支持相邻句子；
- 是否遗漏最强反方；
- 结论是否超出样本和证据；
- 日期、数字、产品状态和链接是否仍然有效。

输出具体问题、文件位置和修改建议，不只给分数。

### 审读二：作者声音与 AI 痕迹

检查：

- 哪些段落没有作者一手增量；
- 哪些段落过度确定、过度完整或像导师说教；
- 是否堆叠对称排比、伪金句和机械总结；
- 是否存在重复论点、假对立或模板化转折；
- 文章中的犹豫、代价和未知是否被润色掉。

随后运行：

```bash
node scripts/check-ai-flavor.mjs <article>
```

脚本只检查少量可确定句式，不能代替语义审读。

## 6. SEO、GEO 与站内链接

文章内容稳定后再处理：

- 标题与搜索承诺一致；
- `description` 是纯文本且能独立说明文章价值；
- `tldr` 只提炼正文已经证明的结论；
- FAQ 只添加真实搜索问题，不为了 schema 凑数；
- Answer-First 适用于教程和解释型文章，叙事随笔不强行套用；
- 内链优先连接前因、补充证据和后续实践，不只链接相同标签；
- 标签从 `config/tags-mapping.json` 选择；
- 日期使用已经到达的上海时间 `+08:00`。

运行 GEO 审计，把它当提示而不是总分：

```bash
npm run geo:audit
```

## 7. 封面

标题与核心视觉隐喻稳定后才生成封面，避免文章改题后视觉仍停留在旧方向。

```bash
npm run covers -- --file <article>
npm run covers:write -- --file <article> --variants 3
```

先 dry-run 检查提示词。候选图需要人眼确认：

- 是否准确表达文章，而非泛化的“AI 大脑/机器人”；
- 是否与站内近期封面重复；
- 中英文文字是否需要独立版本；
- 移动端缩略图下是否仍可辨认。

## 8. 评分模型

语义评分满分 100，目标不低于 90：

| 维度 | 分值 |
|---|---:|
| 命题与论证完整性 | 20 |
| 作者一手增量与在场感 | 20 |
| 事实、证据与引用质量 | 20 |
| 反方、代价与适用边界 | 10 |
| 长期价值与原创解释 | 10 |
| 搜索意图、SEO/GEO 与内链 | 10 |
| 结构、语言与作者声音 | 10 |

以下任一项出现时，无论总分多少都不能通过：

- 编造作者经历、动机、对话、数据或项目结果；
- 关键事实无来源且正文把它当确定事实；
- 引用与相邻结论不匹配；
- 核心命题不是 brief 已确认的判断；
- 泄露 brief 中的隐私或可识别第三方信息；
- E 级 AI 味检查未清零；
- 生产构建失败或封面链接失效。

评分必须附带扣分证据和修改建议。低于 90 时只针对扣分项修订，然后重新评分；不要为了涨分无边界扩写。

## 9. 确定性质量门

至少运行：

```bash
node scripts/check-ai-flavor.mjs <article> --check
npm run frontmatter:check
npm run tags:check
node scripts/generate-content-index.mjs
hugo --minify --environment production
```

根据文章类型补充链接、代码和页面验证。确定性检查全部通过、语义评分达到 90，brief 才能进入 `ready-to-publish`。

## 10. 发布与回执

自动化到 `ready-to-publish` 为止。作者确认标题、核心判断、隐私和封面后才能发布。
文章文件一旦进入 `content/` 就按可发布内容处理；发布等待通过分支合并和部署完成，不再由 front matter 字段控制。

发布后更新 brief：

- `status: published`；
- `article`；
- `public_url`；
- 最终分数和检查结果；
- `published_at`；
- 值得回流上游的争议、反馈和新问题。

上游 `brain` 在 T+3/T+7 通过 `retro` 消费这些结果。博客仓库不直接修改上游知识卡。
