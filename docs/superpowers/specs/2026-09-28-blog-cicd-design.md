## 1. 目标与已确认决策

作者希望把常见内容错误的检查接入 CI/CD，并结合现有双语 Hugo 博客减少重复构建、统一验证入口、理顺发布后自动化。触发案例是英文 GoReleaser 文章的表格分隔行损坏：Hugo 构建成功，但页面显示原始 Markdown。

已确认选择 A：Netlify 承载主站，GitHub Pages 保留为手动发布的备用静态站。作者随后确认了“GitHub Actions 编排检查与发布，验收构建产物后部署 Netlify，确认上线版本后触发下游”的方案。

成功标准：

- 新增的确定性内容错误在发布前被拦截，提示文件、行号、规则与修复方向。
- 每次生产发布只生成一份站点产物，浏览器检查和上传使用同一份产物。
- 普通 Markdown 修改运行轻量检查及定向渲染验收；共享渲染变更扩大测试范围。
- 不以“工作流全绿”“等待两分钟”或 HTTP 200 推断指定版本已上线。
- 日报、Newsletter、搜索引擎通知、README 更新能够独立失败和重试，保留现有业务政策。
- 有明确迁移步骤和回退入口，切换前保留当前发布能力。

继续遵守仓库约定：允许直接推送 `main`，不引入强制 PR；中文和英文保持现有路由；文章日期用 `+08:00`；不增加 `draft`，不自动创建英文占位文章；BEAR OS 保持 Products 默认视图。上游 brief 的作者确认边界不变。

## 3. 目标结构与责任

主链按固定提交执行：识别改动 → 源文件检查与相关离线测试 → 构建、插件处理及函数打包 → 产物与浏览器检查 → Netlify 发布 → 线上验证 → 发布后任务。

| 模块 | 输入与输出 | 责任边界 |
| --- | --- | --- |
| 改动分类器 | Git 事件、明确的基线与目标提交 → `change-set` | 只决定检查范围和是否需要发布，不修改内容 |
| 源文件检查器 | 文件集合、规则、精确历史例外 → `quality-report` | 确定性错误和建议分级，返回明确退出状态 |
| 构建器 | 固定提交、工具版本、站点上下文 → 可部署产物及清单 | 生成内容索引、Hugo 页面、Critical CSS、函数包 |
| 产物验收器 | 同一产物、页面映射、检查范围 → 验收结果 | 检查结构、资源、SEO 和浏览器表现，不重新构建站点 |
| 发布适配器 | 已验收产物、生产凭据 → 部署编号和状态 | 校验来源及文件摘要，上传产物，不重跑 Hugo |
| 线上验证器 | 部署编号、版本标记、域名 → `release-receipt` | 区分上传成功、主域名切换完成、关键行为通过 |
| 发布后适配器 | 已验证回执、实际发布差异、业务状态 | 调用现有推送、邮件、README、性能任务，独立记录结果 |

业务规则放在可本地执行和测试的脚本中；YAML 只负责触发、依赖、权限、缓存与 artifact 传递。共享环境安装收敛到一个仓库内复用入口，不建立通用 CI 平台或自定义任务调度服务。

目标公开命令为 `quality:source`、`quality:output`、`quality:test`、`site:build`、`site:verify`。命令接受显式文件集合或产物目录；部署命令与普通质量命令分离，运行本地检查不会发布。现有 `frontmatter:check`、`tags:check`、`redirects:check` 等继续可用，通过统一入口组合。

## 4. 改动范围与增量规则

| 改动类别 | 验证范围 | 是否发布 |
| --- | --- | --- |
| 普通文章、其媒体或文章数据 | 变更文章及已存在的双语对应页，相关页面渲染验收 | 是 |
| 模板、主题、CSS、JS、路由、Hugo 配置、渲染依赖 | 全站确定性检查，双语代表页浏览器矩阵；按影响运行组件套件 | 是 |
| `netlify/functions/`、内容索引生成器 | 函数单测、打包及生成索引一致性，站点基本验收 | 是 |
| CI、构建或质量检查脚本及规则 | 工作流契约测试、全量质量扫描；构建/部署实现变化执行发布演练 | 影响产物或发布机制时是，否则否 |
| 纯维护文档、README、Newsletter 状态 | 文档或状态格式检查 | 否 |
| SEO 观测快照 | 对应数据契约与 SEO 测试 | 否 |
| 未分类的路径 | 保守执行全量相关检查 | 默认是 |

不笼统忽略 `data/seo/**`。只有现有观测器明确产出的文件模式进入不发布清单；`data/seo/indexable_tags.yml` 等被模板读取的配置仍是发布输入。增加忽略规则时必须有“哪些页面或函数读取此文件”的证据及测试。

PR 以目标分支 merge-base 比较，push 以事件 before SHA 比较；全零 before、不可用历史或强制变更采用明确的全量检查。删除和改名要检查旧 URL、重定向及引用方，不仅检查仍存在的源文件。质量配置变化也触发全量检查。无法证明差异时不返回空集合冒充无需验证。

检查范围和发布通知范围分开：通知使用“上次已验证生产版本 → 本次生产版本”的差异，覆盖多提交 push 和被更新版本取代的中间提交。日期到达后才进入生产的 future content，也由发布页面清单差异捕获。删除页面不进入新文章通知列表。

## 5. 内容检查设计

### 5.1 源文件层

复用仓库已有标签、禁止 draft、空引用、重定向、交互数据和中文 AI 味检查。当前 front matter 检查主要检查 `draft`，需补上必填项、字段类型、纯文本摘要、文章日期显式时区等确定性规则。摘要长度、标签数量、文风建议先作为警告，不把所有旧文章一次性判为失败。

引入锁定版本的 markdownlint，启用有实际故障依据的规则，首先覆盖表格边界、列数与邻接空行。额外检测“看起来是表格，但未被 Markdown 解析器识别”的分隔行，捕获本次 `--- ---` 故障。

疑似表格检查使用解析后的块范围及源位置，避开 front matter、fenced/indented code、数学、明确的示例文本；正确处理转义竖线、行内代码、列表或引用中的表格。Hugo shortcode 只屏蔽其语法边界及已知非 Markdown 内容，不整块忽略所有可渲染正文。无法可靠解释的特殊语法先给出精确诊断，不自动重写。

未闭合代码围栏作为博客写作错误检测，注明它是仓库约定而非所有 Markdown 解析器的语法错误。脚本示例、Go 模板和正文中的普通竖线不得误报成坏表格。

### 5.2 构建结果层

以 Hugo 生成的页面映射和 HTML 解析树为准，不通过 Markdown 路径拼出所有 URL，也不使用整页正则代替 HTML 解析。解析器必须接受压缩 HTML 的合法省略结束标签。

检查渲染后的表格结构、可证明应存在的表格、实际引用的本地图片/附件、内部链接及锚点、未展开的 shortcode；复用现有 canonical、robots、sitemap、hreflang 检查。转义的示例代码、外链、动态函数入口和已配置重定向分别处理。允许 HTML 表格的合法合并单元格，不把所有表格强制成相同列数。

源 Markdown 表格与 HTML 对应仅在映射可证明的普通 Markdown 区域执行；复杂 shortcode 采用显式语义契约。GoReleaser 中英名称模板表的 40 行、2 列和首尾变量作为独立历史回归契约保留。

构建后的检查覆盖所有生产 HTML 的确定性结构/引用；浏览器范围按改动缩小。缺失应有页面、检查器崩溃、报告缺失、无效 artifact 均使必要检查失败。

### 5.3 浏览器层

普通文章检查目标页和已存在的双语对应页；共享渲染变更检查首页、文章、专栏、Products 与交互组件代表页。主要矩阵为 Chromium、375px/1280px、浅色/深色；交互组件变更继续运行现有 Chromium/Firefox/WebKit 套件。定时任务扩大全站抽检。

检查表格可见且内容完整、宽表在容器内滚动、正文页面不横向溢出、本地图片可解码和必要控件可操作。新加的外部图片网络失败先报告；不因第三方临时失败阻断全部文章。没有视觉基线的页面不自动引入整页截图快照；失败保留定向截图和 trace。

普通站点 E2E 启动静态产物服务器，移除“验收前重新运行 Hugo server”的做法。交互组件的故障 fixture 放在独立测试产物目录，不能覆盖生产目录或进入部署包。需要函数行为的测试使用本地模拟/隔离请求，不访问模型提供商或实际发送邮件。

### 5.4 存量与例外

先运行全文报告，人工确认历史问题和误报，再建立精确基线。例外包含规则、文件、规范化证据指纹、原因；不只按行号匹配。被改动后的问题证据不同即视为新增，不自动扩大例外。

CI 不生成或提交新基线。更新基线是显式维护操作，报告中展示增减和理由。原有明确硬门禁保持硬门禁；新增规则允许经过审阅的存量例外，但新增错误阻断。周度报告列出剩余存量，不自动修正文案。

## 6. 一次构建与产物边界

固定 Node、Hugo、Netlify CLI、浏览器及依赖版本。以版本化工具链配置为权威输入，Netlify 配置或工作流里必须保留的重复字段由一致性测试验证；本次重构不顺带升级 Hugo 或主题。依赖使用 lockfile 和 `npm ci`，缓存依据操作系统、版本、锁文件和主题提交隔离。

生产构建固定 `https://cubxxw.com`、production 环境和构建时间，不启用 `--buildFuture`。内容索引生成及其函数副本必须沿用现有入口，验收其公开页面范围与生产发布规则一致；不能遗漏 `_generated` 导致 AI 检索函数部署后缺数据。

使用 Netlify 构建生命周期执行现有 Critical CSS 插件及函数打包；产物检查在这些会修改文件的步骤之后执行。CLI 支持分别构建及用 `--no-build` 发布已构建结果，见[构建文档](https://cli.netlify.com/commands/build/)和[部署文档](https://cli.netlify.com/commands/deploy/)。本地开发继续使用 `netlify dev`。

产物包含最终 `public/`、已打包函数、生成索引和经过审核的部署路由/头部配置。清单保存固定源提交、工具链版本、构建上下文、文件摘要、测试范围与结果。文件摘要针对部署文件集合，排除清单自身和测试报告，避免自引用；归档另有完整性摘要。只打包明确的部署文件；不把工作区、`.env`、认证状态或整个 `.netlify` 缓存归档。

部署 job 获取同次受信任 main 运行的产物，校验 artifact 来源和摘要后上传，不重跑 Hugo、插件或修改 HTML。函数打包输出在验收前完成，上传阶段不得静默采用缓存里的另一份函数。实际 CLI 包布局和函数复用行为必须通过迁移演练证明；证明失败即禁止切换生产。

在一次发布中复用产物不代表 PR 构建可以直接晋升：合并后的 main 提交独立构建和验证。PR、外部分支和可写缓存都不能成为生产发布产物来源。

## 7. 工作流编排与部署权限

`main.yaml` 是 push/PR 的统一入口，保留一个稳定的必要结果 job；根据分类器调用相关检查。选择性跳过须输出明确原因和范围；必要 job 的失败、取消或异常跳过都不能被汇总为成功。复用 `e2e.yml` 的测试能力并移除独立重复触发与站点构建。

生产发布由受信任的 main 入口调用专用发布工作流。PR 只验证和生成可审阅测试报告；如需公开 preview，必须通过受信任 main 上的手动入口、验证待测 ref、使用隔离 preview 配置，不给 fork 的执行过程生产凭据。停用 Netlify 原生 Git 构建后，其自动 Deploy Preview 也停止；初版以 CI 产物和受控手动 preview 替代，不假装仍有原生 preview。

生产环境设置 `NETLIFY_SITE_ID` 和专用 `NETLIFY_AUTH_TOKEN`，凭据只在发布/回退所需 job 可用。保留 Netlify 现有函数运行时环境变量，不把模型、邮件等 API 密钥复制进 CI 构建或产物。检查器无需生产密钥即可运行。此次只读检查确认仓库尚未配置这两个发布字段，配置是切换前置条件。

普通验证可以取消旧 PR 运行；生产发布与线上验证使用一个共享串行组，正在发布的任务不自动取消。排队运行在上传前比较 main 的最新发布输入：若已有更新的发布输入则标为 superseded，交给新运行处理；只有维护文档或业务状态变化不使产物失效。回退使用同一个串行组。

不把 GitHub concurrency 当作可靠 FIFO 队列。跳过的中间版本由下一次发布和通知的版本差异覆盖，所有状态可追踪。相关平台语义见[GitHub 并发控制](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/control-workflow-concurrency)。

## 8. 线上版本与发布回执

构建时生成只含公开字段的版本标记，例如提交 SHA、发布标识和构建时间；响应使用专用不缓存规则，不能继承当前全站一小时缓存规则。部署编号由平台返回，保存在运行回执中，避免为填入编号重新修改已验收产物。

线上验证必须同时确认：目标 Netlify deploy 已就绪且是该站当前生产 deploy；主域名版本标记匹配；中英文首页、变更页面、关键资源及必要路由行为通过。只命中 deploy permalink 不证明主域名已切换。HTTP 200、标题文本或工作流 SHA 单独都不构成版本证明。

使用有总时限的重试读取部署状态和版本标记，不使用固定等待。超时输出 `verification-failed`，停止下游，保留部署编号与诊断；若观察到较新部署则记录 superseded，不为旧版本发送通知。需要函数部署证明时使用不会调用外部服务的无效请求或方法检查。

`release-receipt` 包括 schema 版本、源提交、发布输入摘要、artifact 摘要、Netlify deploy ID、主域名验证状态、验证时间、发布页面清单摘要，以及各必要检查的结果。只有完整的 `verified` 回执可以进入下游；缺失、不匹配、来源不受信任的回执全部拒绝。

## 9. 发布后自动化

以复用工作流/脚本接收经验证的回执，保持每种业务独立的权限和状态，不做一个包含全部令牌的大 job。上线成功与下游执行成功分开显示。下游失败不重新构建、不自动回退网站。

| 任务 | 新触发条件 | 保留的政策 |
| --- | --- | --- |
| IndexNow / Baidu | 已验证发布及实际新增/变更的公开 URL | 配额、批次和重试；手动/定时补偿 |
| Newsletter | 已验证发布后的公开 RSS；定时补偿也先确认当前发布版本 | 原有 draft/send 设置、语言标签、首次启动不群发历史文章 |
| README | 已验证发布后的中文 RSS | 更新既有区域，提交仍只涉及 README |
| Lighthouse | 已验证主站版本的定向运行；保留定时观测 | 保留原有断言及日报发布契约，结果附被测版本 |
| 外链检查 | 每周定时扫描与手动执行 | 使用 lychee；缓存、限速、重试，第三方超时不阻断发布 |

移除旧的 push 并行触发、固定 sleep 和废弃搜索引擎 ping 调用；改为现有受支持推送器和 sitemap 验证。下游手动重跑必须选择可核验的发布回执；定时补偿读取当前生产版本，而不是假设 main 最新提交已发布。

网站发布回执作为 GitHub Deployment 的关联记录，并上传该次运行的完整报告 artifact，保留 30 天。跨运行重试从确定的部署记录定位回执，不按“最新成功工作流”猜测。业务持久状态继续由各任务独立维护，artifact 过期时不得把状态未知视为未执行；无完整回执的手动重试需重新验证当前部署并生成恢复记录。

下游开始前再次确认回执所指版本仍是当前生产版本，若已被取代则交由新版运行或定时补偿处理。读取内容使用该 deploy 的固定 RSS/页面版本，业务 URL 仍采用主站 canonical；不混用新旧 RSS。Newsletter 和定时补偿共享原有业务串行组，README 与状态提交继续显式暂存并处理 main 前进，不覆盖作者改动。

Newsletter 不能仅依赖最后才提交的 `newsletter-state.json` 保证幂等。以语言和文章 canonical URL 为业务身份，先持久化发送意图及 attempt ID，成功后才调用提供商；收到结果后记录邮件 ID。创建结果或状态持久化结果不明时保留 pending 并标为 `needs-reconciliation`，通过提供商记录核对后再恢复，禁止自动盲重发。状态格式迁移兼容原有 sent 记录，不把旧记录当未发送。本次改造不宣称实现分布式 exactly-once，不自动提升发送权限。验证使用 dry-run，不向订阅者发送测试邮件。

SEO Snapshot、Analyze、Autofix 保留现有 API、数据 schema、UTC 日报日期、模型只读边界、proposal-only 政策和 `daily-report-publish` 串行约定。内容发布时间仍用上海时区，两者不可混同。`seo-contracts.yml` 的已有语义测试继续覆盖工作流变化；日报引用不使用关闭 issue 的关键词。

## 10. Pages 备用站

`hugo.yml` 只保留 `workflow_dispatch`。默认使用受信任 main；选择历史版本时要求完整、可验证的 main 历史提交。使用相同源码检查和构建逻辑，但以 Pages 子路径上下文单独构建，不能上传主站的绝对路径产物冒充可用备用站。

备用站验证中英文入口、资源子路径和主要导航。统一 noindex，并保持文章 canonical 指向主站；产物检查显式使用 backup 上下文，不能误套主站的自引用 canonical 和可索引要求。不发送 Newsletter、IndexNow 或 SEO 发布通知。Netlify Functions 与平台重定向不可用，备用 UI 应隐藏对应交互或明确指向主站，避免留下可点击但失效的 AI/订阅入口。

备用站不自动接管主域名，不承诺自动容灾，不与生产发布并行触发。

## 11. 迁移与回退

迁移按三个可验收阶段执行，不把“代码合并”等同于“主站切换完成”。

1. **影子验证**：引入共享检查、工具链配置和产物验收；现有 Netlify 发布继续工作。新链路只生成报告和隔离的 draft deploy，外部通知全部 dry-run。建立历史基线；保留现有回归契约。必须验证 Critical CSS、函数包、生成索引、重定向与 headers 的等价性。
2. **生产切换**：配置专用凭据，记录当前生产 deploy 作为回退点；短暂冻结自动生产发布，确认没有旧的在途发布；停用 Netlify Git 云端 builds，启用 Actions 发布入口，对固定 main 提交执行首次生产发布。期间不得同时保留两个可自动发布主站的入口。版本及行为验收失败立即停止后续通知，进入回退处理。
3. **收敛旧入口**：首次生产验证成功后启用下游正式触发，将 Pages 改为手动，移除重复构建及固定等待；保留迁移记录、运行手册和手动回退入口。

Netlify 官方支持停止云端 builds 后使用 CLI/API 发布已构建产物，见[构建配置说明](https://docs.netlify.com/build/configure-builds/overview/)。停用操作属于平台配置，实施时需核验实际生效；仅修改仓库 YAML 不算完成。

自动验证失败不会自行恢复平台配置或盲目回滚。手动回退选择已验证的历史 Netlify deploy，使用串行入口恢复该 atomic deploy 后重新核验主域名；不重建旧源码，不重复触发文章通知。若需退回旧发布体系，先停用 Actions 自动发布，再恢复 Netlify Git builds。平台回退能力与自动发布覆盖风险见[Netlify 管理部署文档](https://docs.netlify.com/deploy/manage-deploys/manage-deploys-overview/)。

## 12. 验收证据

| 场景 | 必须观察到的结果 |
| --- | --- |
| 英文表格分隔行重新插入 `--- ---` | 源文件检查报到文件/行，且生产发布不执行 |
| 表格合法转义、代码示例、列表内表格、HTML 合并单元格 | 无误报；中英 fixture 均覆盖 |
| 压缩 HTML 省略合法结束标签 | HTML 检查仍正确识别表格 |
| 新增坏图片/内链/锚点或损坏代码围栏 | 对应规则报告；合法 shortcode 示例不误报 |
| 普通文章与共享 CSS 分别变更 | 运行范围不同且符合分类规则；必要检查不可被异常 skip 绕过 |
| README、Newsletter 状态、SEO 快照变更 | 不触发主站发布；索引策略配置变更仍触发 |
| 合并提交、改名、删除、多提交 push、历史不可用 | 分类器正确处理，通知不只取最后一个提交 |
| 上传前 artifact 被修改或来自 PR | 发布拒绝 |
| Netlify 上传成功但主域名仍是旧版本 | 不生成 verified 回执，不执行下游 |
| 两个生产运行竞争、旧运行手动重试 | 旧产物不覆盖已发布的新产物；回退另走明确入口 |
| Newsletter 创建成功但记录保存失败 | 不自动重复创建，进入核对状态 |
| 下游失败后重试 | 网站不重建；已完成业务按其持久状态跳过或核对 |
| Pages 手动部署 | 子路径和双语可读、noindex、无误导性函数交互、无外部通知 |
| 生产回退演练 | 主域名恢复指定 deploy，版本与关键行为通过 |

报告区分本地/fixture 证据、CI 证据和实际线上证据。必须记录提交 SHA、检查范围、运行链接、部署编号；未执行项目明确标记，不借用其他提交的绿灯。记录迁移前后同类改动的构建次数、耗时和失败定位步骤，以实测评价优化，不预先承诺提速比例。
