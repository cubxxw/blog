# Products 页首次加载、语言切换与声音分析

日期：2026-10-27（新加坡 / 上海，UTC+08:00）。代码基线：`cffe3d41`。本轮先从远程快进同步 31 个提交；原有 `output/` 未提交内容保留。

结论：首次进入的主要等待发生在三维房间的资源、初始化和首帧门槛；切换语言会重建整个房间；音频需要完整下载并解码，缺少状态反馈会让等待看起来像点击失效。应该分别解决这三个阶段，不能用一个页面加载分数代替体验验收。

## 实际证据与边界

在线中文入口为 https://cubxxw.com/zh/projects/ 。本轮在新 Chrome 会话中读取 Navigation / Resource Timing、加载进度和房间状态，并检查源码。一次冷启动的 HTML 首字节约 0.93 秒，首次内容绘制 2.04 秒，load 事件 3.40 秒；但这时房间还未就绪。HTML 解压后 314,109 字节，Brotli 正文约 80,413 字节。这里的首次内容包含加载提示，不能视为房间已可操作。

同一次观测里，墙面颜色贴图 686,726 字节，资源持续约 17.94 秒；部分图片随后出现 `ERR_CONNECTION_CLOSED`，房间走入失败恢复。再次加载也遇到首帧超时。这些是该会话的网络/设备条件，不能推断所有访问都需要相同时间，也不能把它当成稳定的访问分位数。

源码和观测一致显示：首帧前同时发起材质贴图、猫模型、多张照片、艺术品和三张窗景图片。初始观测为约 254,952 个三角形、342 次绘制调用；这是当时场景的一帧数据，不是所有视角的峰值。`data-ready=true` 只代表桌面脚本已经挂载，当时 `data-boot-state` 仍为 loading，不能用它验收首屏。

页面内 `data-space-catalog` 为 175,238 字节，约占解压 HTML 的 56%；含本语种 192 篇文章和另一语种 177 条阅读路径。另有约 18 KB 的知识图数据和默认不可见的 Product Lab 模板。网络已经压缩这些内容，但仍要传输、解析，并有数处重复解析目录 JSON。

仓库保存的 [2026-10-26 PSI 原始结果](../../data/seo/psi-2026-10-26.json) 对英文 Products 页给出：移动端性能 33、LCP 10.868 秒、主线程总阻塞 20.718 秒；桌面端性能 36、LCP 7.2245 秒、总阻塞 19.568 秒。该历史快照缺少部分设备/限速参数，没有可用的页面真实用户样本；只能作为问题线索，不能据此与本轮开发环境作提升百分比比较。

## 首次进入：缩短真正需要等待的链路

当前已有正确措施：桌面、控制器、Three.js 和选中房间模块并行预取；Product Lab 的 DOM 延迟展开；首帧后才执行六面反射捕获；加载提示没有人为停留时间。继续优化应集中在剩余瓶颈。

优先处理窗景和照片。当前正确窗景决定首帧能否揭开，不能为了快先露出与用户所选时间不一致的旧景。可先加载同一窗景的小尺寸版本，再替换高清图；将这张关键图提早声明为图片预加载。墙面/地板优先使用屏幕实际需要的尺寸，高清法线、粗糙度与远处照片后补。照片墙里的部分缩略图仍直接使用文章原始 JPG，宜生成固定尺寸派生图。低带宽时减少争抢，正常网络保留最终画质。

接着拆分初始运行代码和内容。房间进入只需要场景控制、基础桌面、少量最近文章和入口。完整文章目录、地图/相册、助手、知识图以及 Product Lab 的数据和专用样式可以在首次需要前加载。`apps.js` 当前静态引入媒体、助手和浏览器模块，动态导入再深一层才有实际收益。默认视图、文章入口和无脚本可读路径要保留，不能把所有内容都推迟到一个空白按钮后。

三维侧需要单独测 CPU 和 GPU。压缩文件能省下载时间，不能省重新构建几何体、生成 Canvas 纹理、上传贴图和编译着色器。可将重复家具和小物件合批、复用材质/几何体，分批初始化首屏外物件；绘制调用比单纯减少脚本字节更值得检验。硬件路径目前像素比上限 1.5、阴影 1536；软件渲染已有 384,000 像素和 512 阴影预算。后续可按实测帧耗时逐步提高画质，不能仅凭手机/桌面标签判定能力，也不宜重新引入阻塞首帧的同步 GPU 预热。

体验上，需要测三个时刻：加载提示首次出现、正确房间首次可见、关键操作首次可用。若资源失败或超时，恢复入口必须能打开可用的工作区，并说明发生了什么。当前资源失败不是音乐按钮本身的错误，但房间失败会让音频控制器根本没有机会初始化，必须在整体旅程里观察。

## 语言切换：保留房间比重复下载优化更有效

`desktop.js` 的 language 分支最终调用 `location.assign()`。它会保存笔记、收藏和窗口状态，也有 locale-resume 标记，但浏览器随后销毁当前页面。模块可能命中缓存，三维场景、纹理、着色器、相机和音频仍会重新初始化。当前机制也不能承诺音乐不断、相机位置不变。

短期可在用户聚焦或悬停语言按钮时预取另一语言的 HTML/文案包，并立即显示切换反馈、避免重复点击；应尊重节流网络和省流量偏好。指纹化的场景和桌面脚本也可单独配置长期 immutable 缓存，避免它们继续落入 `/js/*` 的一小时规则。但这只能改善网络部分，不能消除重建成本。

建议的长期方案是只在 Products 内做原地换语言：保留唯一的房间渲染器和声音引擎，加载另一语言的数据包，更新按钮、帮助、文章/产品目录以及语言相关链接；同步更新 URL、页面语言、标题和导航历史。传统中英文 URL 继续由 Hugo 生成，直接进入、刷新和搜索收录仍有完整页面，不引入整站前端框架。

这需要先抽出语言适配层。现在 `zh` 和 `t()` 固定在多个模块闭包里，不能只替换几个 DOM 文本就宣称完成。必须覆盖场景提示、物品详情、窗口、菜单、助手、书架、对话框和错误反馈，并保护输入法组合态、笔记选区、滚动位置、当前相机、所选唱片和播放进度。加载失败时保持原语言可用，允许再次尝试；前进/后退也要可靠恢复。

验收应直接断言：切换语言不创建第二个 WebGL context，不销毁当前音频 source；相机、笔记和窗口保持；本地已缓存文案切换目标低于 100 毫秒。冷文案加载单独计时，不能把网络等待隐藏在动画里。这些是建议目标，目前尚未实施，也没有已达标证据。

## 声音：本轮实际修复

房间原先明确传入 `defaultEnabled:false`。独立音频引擎用 fetch 读取完整文件后才调用 decodeAudioData：默认曲目 2,786,222 字节，雨声 FLAC 18,420,389 字节。仅以 1 Mbps 净吞吐量估算，前者下载下限约 22 秒，后者约 147 秒，尚未含延迟和解码。播放器又缺少载入提示，用户很容易继续点击，从而取消仍在进行的播放。

本轮已完成以下局部改动：

- 房间默认保留播放音乐的意图；浏览器允许时自动开始，被拦截时在首次真实点击/按键继续启动。手动关闭音乐会持久保存，安静模式和零音量仍然有效。
- 先恢复浏览器声音权限，再请求完整文件，避免播放被拒绝后仍下载两个大文件。取消、换曲和离开页面的旧异步结果继续受现有 token / generation 保护。
- 唱片面板显示载入、取消载入、失败重试、浏览器待授权、静音及安静模式。按实际 source 的状态显示播放/暂停，不把“想播放”当成“已播放”。
- 修复首次面板播放可能被 root 捕获监听先恢复、再由同一次按钮操作取消的冲突；明确按钮操作由它自己的处理函数负责。
- 网页雨声改为从原有无损片段生成的 128 kbps、44.1 kHz 双声道 MP3，1,729,140 字节，减少约 90.61%。原 FLAC、来源和许可记录保留，新增派生记录与文件摘要。原有 8 秒解码边界交叠继续工作。

“第一次进入、不碰页面、保证有声”无法由网站保证。[Chrome 自动播放策略](https://developer.chrome.com/blog/autoplay/) 与 [Safari 自动播放说明](https://webkit.org/blog/7734/auto-play-policy-changes-for-macos/) 都要求处理浏览器拒绝播放的情况。网站可以尝试自动开始、保留真实操作后的启动、记住暂停偏好，但不能伪造用户操作来绕过限制。Safari/iPhone 的原生策略和实际外放听感仍需单独验收。

进一步的音频优化是让完整音乐按流播放，避免等待整首解码。它与当前依靠解码缓冲区实现的无缝采样时钟循环存在取舍，需要验证循环接缝和后台播放。只压缩雨声解决不了曲目自身的等待。按当前 44.1 kHz 双声道 Float32 估算，两个播放缓冲区本身仍约 96 MB，解码/交叠时会有额外临时内存；这是计算估算，并非实测内存占用。

## 建议的实施次序与验收

| 顺序 | 工作 | 成本与主要风险 | 需要观察的结果 |
|---|---|---|---|
| 本轮 | 声音默认意图、正确反馈、权限前零音频下载、雨声派生版 | 小；保护暂停、取消与循环 | 音频状态和原生播放通过，文件减少 90.61% |
| 下一批 | 正确窗景小图先到、照片缩略图、关键资源优先级 | 中；尺寸和色彩切换可能影响画面 | 相同设备/网络下正确首帧 p75 改善，最终画面对齐 |
| 下一批 | 将全文目录和非首屏应用从启动路径拆出 | 中；首开应用可能出现额外等待 | 首屏字节/长任务下降，应用点开有立即反馈且可重试 |
| 独立改造 | Products 原地切换语言 | 中到大；多模块文案、历史与输入状态 | context/source 身份不变，笔记、相机和播放不断 |
| 后续 | 按实测能力分级画质、合批、音频流式播放 | 中到大；画质、循环与后台兼容 | 首帧、交互延迟、帧耗时和内存分别改善 |

要在同一发布版本上分别测中文/英文、冷缓存/热缓存、桌面/移动、正常网络/限速网络。建议记录正确房间可操作时间、语言点击到文案完成时间、声音点击到真实 source 开始时间、输入延迟和长任务。LCP 可以辅助判断首屏，但 WebGL 画面和加载提示需要自定义时刻配合；参考 [web.dev 的 LCP 分阶段优化说明](https://web.dev/articles/optimize-lcp)。

## 验证记录

新增问题先以失败测试复现，再实现修复；包括权限前提前下载、暂停偏好未恢复、无加载反馈，以及按钮捕获阶段的取消竞态。声音、音量、循环、来源和家具联动的定向测试共 76 项通过；其中音频引擎与控制/界面相关为 67 项。启动定向测试另有 18 项通过。独立只读审查没有未解决的明确问题。

生产 Hugo 构建与 TypeScript 检查通过。通过 Netlify Dev 打开中文页，观察到房间 complete、音乐与雨声均为 playing；唱片面板真实点击暂停后，按钮恢复为“播放音乐”，暂停偏好写入 no。这里验证了浏览器中的 source 状态，没有声称进行外放听感评价。

首次执行既有自动浏览器回归因本机缺少 Playwright 对应 Chromium，7 项均未启动；下载 182.1 MiB 的指定浏览器时网络过慢，未完成该套执行，不能将其计为通过。

随后使用系统 Chrome 156.0.8078.48，对生产构建做了六项补充检查：模拟拒绝自动播放时零音频请求；真实首击启动两个原生 source；唱片面板暂停并记住偏好；慢请求显示载入与取消；503 后显示重试且重试能播放；390×844 下唱片控制可见。音频解码、source 与用户输入均使用浏览器原生实现，拒绝自动播放由受控的权限边界触发，不能替代 Safari/手机原生策略验证。六项通过，没有 pageerror；移动端截图已人工查看。结构化结果见 [Chrome 验证记录](evidence/2026-10-27-products-audio-chrome.json)。

本轮没有实施原地语言切换、照片派生与三维合批，因此没有这些项目的性能提升数据。技术修复按仓库默认流程提交，完整 Linux 浏览器矩阵与线上部署结果需另行读回。
